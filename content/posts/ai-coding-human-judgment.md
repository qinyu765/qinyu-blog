使用 AI 编程时，我越来越想弄清楚：哪些事情值得自己持续关注，哪些可以交给 Agent 自主推进。Agent 在这里指能探索代码、修改文件并执行验证的 AI 助手。

这个问题也来自一种阅读负担：计划、实施说明、验收报告都很完整，但文字一长，我就不想读完，读到后面也容易丢失注意力。开发还在继续，我对项目的理解却可能停在上一次认真阅读的时候。

在上一篇[《Plan 模式已死》](/blog/plan-mode-is-dead)中，我讨论了决策的时机。这篇想接着回答：**让 Agent 自主执行以后，人应该主导什么，又需要它怎样表达，才能跟得上？**

## 我想把注意力放在四件事上

我把需要持续掌握的内容整理成了四项：

| 关注点 | 我需要回答的问题 |
| --- | --- |
| 目标与需求 | 要解决什么问题，什么表现才算做好？ |
| 关键取舍与成立前提 | 接受了什么成本和限制，这个设计依赖哪些假设？ |
| 验证依据 | 凭什么说做完了，证据覆盖到哪里？ |
| 必要的系统理解 | 核心流程怎样运行，出了问题从哪里查起？ |

前两项决定方向，第三项帮助判断交付是否可信，第四项支持后续维护。函数怎么拆、文件放哪里，可以由 Agent 结合项目约定处理；这些细节影响到上面的问题时，就值得我深入看。

这张表也有一个使用边界：它是检查维度，每次汇报只展开与当前变更有关的部分。改一个按钮颜色，没必要再介绍整套架构。

## 一次图片上传，包含三种不同的判断

拿一个假设的图片上传需求来说。

从产品角度，我需要确认用户要完成什么：上传后能否预览，刷新后能否继续访问，失败时怎样恢复。只写“支持上传”，很容易把这些差异留给实现者自行决定。

从架构角度，我需要理解图片存在哪里，谁有权访问，数据库保存什么，以及未来更换存储服务要付出多少工作。这些选择会影响费用、权限和后续变化的成本。

从测试角度，我需要知道成功路径和失败路径经过了什么检查。请求返回成功，不一定证明图片地址已经正确保存；刷新后能打开，也不能直接证明访问权限符合要求。

这里还要分清两件事。**代价需要权衡，前提需要核实。** 选择某个存储服务，迁移会增加工作，这是代价；当前按单人使用设计，这是前提。以后要支持多人协作，就应该回到这个前提重新判断。

同一个功能，代码可以连续完成，判断却要从不同方向进入。

## 产品、架构、测试的责任会怎样变化

梳理到这里，我发现这些问题都很熟悉：产品判断要不要做、怎样才算满足需求；架构判断接受什么约束、怎样承受变化；测试判断用什么证据支持交付。

这些一直是开发中的重要工作。AI coding 让我更直接地面对它们：当 Agent 能够跨过多个环节持续执行时，原先由不同岗位分别把关的判断，仍然需要有人接住。

产品工作需要能被检验的成功条件，架构工作需要能随证据修正的取舍，测试工作需要能揭示错误假设的反馈。它们的价值，也应当在开发过程中体现出来。

我认为，这会挑战以环节和文档交接为中心的职责划分。一个人借助 Agent 可以参与更宽的工作范围，同时也要知道自己在哪些地方缺少判断依据。复杂问题仍然需要专项经验和独立审查，职责的交叉不会自动补齐这些能力。

判断本身也可以由 AI 协助，部分可以在明确边界内自动完成。更需要说清楚的是：谁设定目标，谁认可代价，谁有权接受尚未验证的部分。

**可以委托执行，也可以委托分析；接受什么结果和后果，需要有明确的责任归属。**

## “测试通过”还需要解释它证明了什么

如果实现和测试都交给 Agent，它可能依据同一份错误理解，写出彼此一致的代码和测试。

因此，我更关心验证能否对实现形成有效约束。对于图片上传，至少可以从使用者的行为出发：上传、保存、刷新，再检查图片是否仍然可见；失败以后，检查是否有清楚的反馈，以及能否恢复操作。

“做了哪些验证”还应该包含验证的边界：使用了真实服务还是替代环境，检查了界面还是只检查逻辑，哪些情况尚未运行。

一个能支持判断的汇报可以是：

> 上传后保存图片地址、刷新后读取地址的逻辑已通过测试。真实存储服务下的上传、权限和超时情况尚未验证，因此还不能确认完整流程已经可用。

这段话让我知道当前证据支持到哪里，也知道下一步还缺什么。

## Agent 的表达，也影响我能否掌握开发

即使关键判断都做了，如果埋在长篇报告里，我仍然可能错过它们。

我希望重要汇报能先回答：发生了什么，对当前目标有什么影响，根据是什么，以及是否需要我介入。完整的执行记录可以保留，并提供查看入口。

表达方式也应该由问题决定。比较方案适合表格，解释数据流适合简图，界面变化适合前后截图。一个结论用一句话就能说清时，也不必套上固定模板。

我还需要区分“值得知道”和“需要批准”。已有授权范围内的重要选择，Agent 可以实施后解释；遇到超出边界、需要我权衡目标的选择，再停下来讨论。这样能让我关注重要变化，也避免被普通实现细节反复打断。

社区里有两份规则给了我具体启发。Matt Pocock 的 [`wait-what`](https://github.com/mattpocock/skills/blob/main/skills/productivity/wait-what/SKILL.md) 用来在回答没讲明白时，补必要背景并重新解释；[`pr`](https://github.com/mattpocock/skills/blob/main/skills/engineering/pr/SKILL.md) 则要求用简洁视图说明变化，配上前后证据、可逆性和影响范围。我想借鉴的是这些组织信息的方式，中文效果还需要在实际任务中试。

对我来说，阅读负担也提醒了一个更大的问题：当一个人能借助 Agent 推进更多工作时，他仍然只有有限的注意力。报告需要帮助他找到值得判断的地方。

下一次 Agent 交付功能，我会先检查自己能否回答四个问题：它符合什么需求，接受了什么代价，有什么验证依据，以及系统发生了什么重要变化。答不上来的那一项，就是接下来值得补充解释或验证的地方。
