AI coding 用久以后，我越来越确定一件事：让 AI 把代码改对，只是工程工作的一部分。

我平时会给 Codex 一组很强的约束：先读现状，只完成当前需求，不做无关重构，不扩大修改范围，最后跑验证再交付。这样的方式安全、可审查，也很适合日常开发。

但它有一个不容易察觉的副作用：注意力一直停留在“这次改哪些文件”，项目的模块边界、依赖方向和未来变化成本，就可能被放到很后面。

于是我产生了一个具体想法：**把架构判断从普通开发对话里单独拿出来，做成一个可以按需触发的 Skill。**

这不是让每个需求都变成大重构，而是让 AI coding 有两种清楚的工作模式：常态做最小变更，需要时再大刀阔斧。

## 最小变更为什么重要

“只做必要修改”并不是保守，而是一种很有效的风险控制。

| 它带来的好处 | 对日常开发的帮助 |
| --- | --- |
| 修改范围小 | 更容易理解和审查 |
| 不碰无关代码 | 减少回归和意外副作用 |
| 先验证再交付 | 更容易定位问题和回滚 |
| 不预先抽象未来需求 | 避免为了想象中的场景增加复杂度 |

这些原则应该保留。问题在于，最小变更解决的是“这次怎样安全完成”，不一定能回答“这个项目以后怎样继续变化”。

如果每次新需求都只是在同一个模块里追加一个分支，短期看每次都很小，长期可能形成越来越难理解的边界。真正的摩擦也许不在这一行代码，而在职责划分、接口设计或依赖关系。

所以我不想放弃最小变更，而是给它加一条升级路径：当局部修补开始反复出现，就暂停一下，先做架构评估。

## 问题不是 Codex 不会架构

普通需求提示词通常已经把任务范围限定得很窄：修一个 bug、补一个接口、加一个页面。模型会优先满足这个目标，这正是我们希望它做的事。

但“项目是否应该继续沿用当前边界”往往不在当前验收条件里。如果没有显式提出，架构问题就很容易被当成背景噪声。

我后来把两类问题分开：

- **开发模式**：当前需求怎么以最小风险落地。
- **架构模式**：当前结构能否承受下一轮变化，应该在哪个边界上投入设计。

这两个模式不是谁替代谁。开发模式负责交付，架构模式负责在必要时改变交付的方式。

## 这个 Skill 要输出什么

我把 Skill 命名为 [`evolve-software-architecture`](https://github.com/qinyu765/evolve-software-architecture)，名字里特意用了“演进”，而不是“完美架构”。

它的目标不是一次性设计出未来十年的系统，而是降低下一次变化的成本。一次完整的架构评估，至少要把下面几件事说清楚：

1. **项目事实**：技术栈、模块边界、构建和测试方式、已有文档与历史决策。
2. **真实摩擦**：哪些是代码和配置已经证明的事实，哪些只是推断，哪些仍然未知。
3. **优先质量属性**：这次最需要保护的是可扩展性、可靠性、性能、发布安全，还是别的指标。
4. **候选方案**：至少比较两个可行方案，并把维持现状也列出来。
5. **权衡与代价**：成本、风险、可逆性，以及不改变现状可能付出的代价。
6. **迁移与验证**：怎样分阶段实施、怎样回滚、用什么证据判断新边界真的有效。

这个输出契约很重要。没有它，所谓“架构建议”很容易退化成漂亮但无法落地的名词列表。

## “一劳永逸”应该换一种理解

刚开始设计这个 Skill 时，我也会想：能不能这一次就把架构设计得足够好，以后少走弯路？

后来我觉得，“一劳永逸”不应该意味着预先猜中所有未来需求。更现实的目标是：

- 让边界清楚，变化发生时知道从哪里进入。
- 让决策有记录，下一次不用重新猜测背景。
- 让迁移可分步完成，而不是只能一次性押注。
- 让错误的设计可以被发现、验证和撤回。

换句话说，好的架构不是消灭变化，而是降低变化的成本。

## 什么时候该大刀阔斧

“需要时大刀阔斧”不能只凭当下的不舒服，也不能等到系统完全失控。我的判断线更接近下面这样：

| 观察到的信号 | 默认动作 | 何时升级为架构评估 |
| --- | --- | --- |
| 单模块、边界稳定、需求局部 | 做最小变更 | 同一边界连续承接不同类型的变化 |
| 修改容易回滚，验收标准明确 | 保持现状 | 为一个需求必须穿过多个不相干层次 |
| 只是重命名、样式或小依赖升级 | 不触发架构模式 | 变化会影响公共接口、多个进程或多个团队 |
| 出现一次特殊分支 | 先完成需求 | 同类例外反复出现，下一次大概率继续复制 |

进入架构模式，也不代表马上重写整个系统。更稳妥的办法是先确认问题是否重复，再找一个最小的垂直切片，验证新边界，最后决定是否扩大迁移范围。

可以把规则记成一句话：**小改是默认路径，大改必须有证据、有边界、有回滚点。**

## 为什么要做成独立仓库

这个 Skill 一开始只服务于 XiLuoLin，但我没有把它直接写死在 XiLuoLin 的项目规则里，而是建立了个人公开仓库：[`qinyu765/evolve-software-architecture`](https://github.com/qinyu765/evolve-software-architecture)。

组织方式也刻意保持简单：公开仓库保存唯一的上游源码；具体项目只保存某个版本的受控副本和来源锁定信息。这样既能在真实项目中使用，也不会让项目副本反过来成为另一个“偷偷发展的上游”。

这么做解决了三个实际问题：

- Skill 有自己的版本、路线图、评测和发布节奏。
- 项目可以审查升级差异，不会因为自动同步而突然改变行为。
- 真实仓库的特殊事实不会自然渗入通用规则。

Skill 本身只保留运行所需的文件；发展规划、架构决策和跨项目评测放在上游仓库。代码和 Skill 都需要单一事实来源，否则维护到最后，最难解释的往往不是规则，而是“到底哪一份算数”。

## 通用化不是把所有项目揉成一套模板

桌面端、Tauri、SDK、Web、CLI 的边界和质量属性不同。把 Web 项目的经验直接套到桌面端，或者把 UI 应用的组织方式搬到 SDK，通常只会制造新的偏见。

所以这个 Skill 采用“核心流程 + 项目类型适配器”的方式：

- **核心流程**只负责事实、摩擦、权衡、迁移和验证。
- **适配器**描述某类项目的识别信号、平台约束、典型边界、常见失误和验证手段。

我会先用 XiLuoLin 做真实纵向案例，但 XiLuoLin 的专有事实只能留在案例和评测里。只有在至少两个性质不同的项目中都成立的规则，才有资格进入核心；只有在多个同类型仓库中重复验证的经验，才进入对应适配器。

这是一种刻意的“慢通用化”。它避免 Skill 因为第一个真实仓库而形成路径依赖，也避免为了追求通用，第一天就做成一套谁都读不完的框架。

扩展边界时，我也会把两个方向拆开推进：先验证其它项目类型能否泛化，再扩展到新需求和新项目时触发skill。一次同时扩展两个方向，出了问题就很难判断是领域适配失败，还是工作流程本身失败。
