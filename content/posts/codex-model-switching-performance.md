如果让 Codex 连续完成一个多步骤任务，中途切换模型，常常会出现一种很难描述的感觉：它还记得前面的对话，却没有刚开始那么“在状态里”。

它可能开始重复已经做过的检查，忘记原来强调过的约束，或者把一个需要整体判断的问题重新做成了局部修补。

核心观点很简单：**模型切换是一场工程交接。**把交接信息写清楚，切换就能成为一套可管理的工作方式。

## 先把“性能变差”拆开

“性能”至少包含四种不同的现象。先分开看，后面的判断会简单很多。

| 现象 | 更可能发生了什么 | 切换模型的影响 |
| --- | --- | --- |
| 切换后的第一轮变慢 | 新请求没有复用相同的提示词前缀 | 主要影响延迟和输入成本 |
| 回复变短、漏掉检查 | 模型能力、推理投入或任务理解发生变化 | 可能影响质量 |
| 任务方向变了 | 原计划没有被当成当前约束重新确认 | 影响工作连续性 |
| 文件状态变得不可靠 | 切换前后的工具结果没有被完整复核 | 影响最终正确性 |

所以，“是不是缓存失效了”只能回答其中一小部分。变慢和变差可能同时出现，诊断时需要分别处理。

## 缓存与判断状态是两回事

OpenAI 的 Prompt Caching 复用的是提示词中**完全相同的前缀**。系统提示、工具定义和稳定的项目上下文保持不变时，后续请求更有机会降低延迟和输入成本；前缀一旦变化，就可能重新处理。[Prompt caching 官方文档](https://developers.openai.com/api/docs/guides/prompt-caching)对此有明确说明。

这能解释为什么切换模型后的第一轮有时更慢。缓存只回答“这些输入是否处理过”；上一个模型为什么选择某个方案，需要从计划、工具结果和决策记录里恢复。

可以把两者想成两种完全不同的东西：

- **缓存**是计算结果的复用；
- **判断**是对目标、约束和风险的理解。

前者影响响应速度，后者影响任务质量。把缓存命中理解成跨模型搬运的完整工作记忆，会高估它的作用。

## 对话记录和完整推理连续性

一个编码任务里同时存在两层状态。

| 状态 | 例子 | 是否容易被看见 |
| --- | --- | --- |
| 显式状态 | 用户要求、计划、工具输出、测试结果、文件 diff | 容易看到 |
| 隐式状态 | 为什么先改这里、哪个风险更重要、哪些方案已经被排除 | 不一定完整呈现 |

Reasoning model 会使用额外的 reasoning tokens 来拆解问题、比较方案和规划工具调用。OpenAI 的官方文档也说明，支持的模型可以在后续请求中继续使用**可用且兼容**的 reasoning items；这些内容保持 opaque，界面只展示结果与摘要。[Reasoning models 官方文档](https://developers.openai.com/api/docs/guides/reasoning)

这句话里最重要的是“可用且兼容”。它描述的是有条件的延续：模型切换后，新的模型通常拿到旧对话、已经产生的工具结果和当前工作区，再重新建立对任务的理解。

模型切换会增加重新解释任务的机会。任务越长，越多关键判断只存在于没有写下来的上下文里，这种重新解释就越容易变成方向偏移。

## 模型档位决定能力起点，推理投入决定工作量

当前 GPT-5.6 模型文档把 Sol 描述为面向复杂专业工作的 frontier model，把 Luna 描述为面向成本敏感、高吞吐场景的模型。两者都可以设置 reasoning effort；effort 只调节当前模型投入多少推理计算，模型之间的能力边界仍然存在。[GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)、[GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

这带来一个很实际的结论：

> Luna 的高 effort 可以让一个边界清楚的执行任务更认真；Sol 在复杂取舍上的判断能力仍然属于模型本身。

适合快模型的任务，通常有明确输入、明确输出和容易运行的验证。架构权衡、含糊需求、跨模块风险和最终审查，则更适合交给判断能力更强的模型。

## 真正容易丢的，是工程上下文

我后来发现，模型切换带来的问题，和我平常使用 Codex 的方式有关。

我的常态提示词一直强调：只做最小必要变更，不顺手重构，不扩大范围，先验证再提交。这套约束很有价值，它能减少误改，降低 review 成本，也让每次修改更容易回滚。

但它也有一个盲点：**它优化的是当前任务的局部安全，未必会主动优化项目未来几个月的演进成本。**

当任务只是“修一个按钮”时，最小变更就是正确答案。当任务已经变成“未来要增加多个 provider、跨进程能力或平台适配”时，继续只做最小 diff，反而可能把问题留在更贵的位置。

这时如果再发生模型切换，新的模型看到的可能是：

- 原来的用户目标；
- 一堆已经修改过的文件；
- 当前提示词里的“不要扩大范围”；
- 但没有一份明确说明“这一次允许为了长期边界做更大调整”的工程判断。

它当然更容易回到局部修补。你会感觉模型变笨了；更准确地说，任务模式没有交接清楚。

## 这也是我为什么单独做一个架构 Skill

我把“长期架构思考”放进一个单独的 [`evolve-software-architecture`](https://github.com/qinyu765/evolve-software-architecture) Skill，没有继续堆进日常提示词。

原因很简单：日常开发和架构审查是两种不同的工作模式。

日常模式关心：

- 这次需求最小需要改什么；
- 如何不影响已有行为；
- 如何快速验证和交付。

架构模式关心：

- 现在的边界是否会阻碍下一阶段扩展；
- 哪些复杂度应该集中，哪些复杂度不该提前引入；
- 未来变化会扩散到多少模块、进程和测试；
- 是否值得为了长期收益进行一次较大的迁移。

这个 Skill 只在架构评估、跨模块设计、扩展性、技术债方向或重大重构时触发；运行前先识别当前项目是 Desktop、SDK、Web、CLI 还是其他类型。

它的核心输出是一份决策材料：事实、当前摩擦、质量属性权衡、至少两个选项、推荐方向、迁移步骤和验证方式。

这保留了一个重要的默认值：**平时最小变更，需要时才有依据地大刀阔斧。**

## 切换前：留下一个小型交接单

交接单无需重述整段对话，只记录会改变下一步判断的内容：

```text
任务目标：
冻结的关键决策：
不可违反的约束：
已经修改的文件：
已经验证的结果：
尚未解决的风险：
下一步允许执行的动作：
遇到哪些情况必须暂停并询问：
```

这份交接单把隐含判断转成显式约束，重点在于减少重新理解任务的成本。

## 切回强模型：先审计，再继续

切回模型后，先让它把当前工作区当成一个需要接手的项目审计：

```text
请先审阅最初的任务目标、交接单、切换期间的所有工具结果和当前文件 diff。

将之前的执行视为待验证状态，先列出：
1. 原计划中的关键约束和验收标准；
2. 已完成、遗漏和偏离的步骤；
3. 未经授权的文件修改；
4. 测试、边界条件和回滚风险。

完成审计并修正问题后，再继续剩余任务。
```

这里的顺序很重要。先审计能更早发现中间模型对问题的改写，减少偏差继续扩大的机会。

## 一套简单的分工方式

分工时只需看任务的可验证程度：

| 工作阶段 | 更适合的模型 | 关键条件 |
| --- | --- | --- |
| 需求澄清、架构设计、方案比较 | 判断能力更强的模型 | 有隐含约束和长期影响 |
| 已确定的文件修改、格式迁移 | 成本更低或速度更快的模型 | 输入输出边界清楚 |
| 测试运行、日志整理、机械修复 | 快模型 | 结果容易观察和复核 |
| 复杂故障定位、最终审查 | 判断能力更强的模型 | 需要重新提出假设 |

一个阶段的正确性难以通过测试快速判断时，应优先考虑判断能力和审查质量。

## 什么时候应该大刀阔斧

可以用一个问题做判断：**如果继续保持当前边界，下一次同类需求会不会被迫修改更多不相关的地方？**

答案为“否”时，最小变更通常足够；答案为“是”时，再进一步确认：

1. 这个变化是已经出现的真实需求，还是想象中的未来需求？
2. 是否至少有两个真实变化会经过同一个边界？
3. 能否先通过一个可回滚的垂直切片验证方向？
4. 新架构带来的复杂度，是否真的低于它要隐藏的复杂度？

这样做的好处，是把“大重构”从情绪化反应变成一次有证据的工程决策。

模型切换适合被设计成一场交接：计划、约束、文件 diff、测试结果和风险记录共同构成可复用的工作状态。复杂任务固定使用 Sol 完成规划与审查；边界清楚的执行步骤可以交给 Luna max。

下一次切换前，先写下交接单；切回强模型后，先启动审计。这样既保留成本弹性，也让关键判断有地方可追溯。
