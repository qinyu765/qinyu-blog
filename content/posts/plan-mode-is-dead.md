我开始怀疑，把「先完成计划，再开始编码」当作 AI coding 的默认流程，会让我们在最不了解项目的时候，做出最多的决定。比起把开工前的计划写得更完整，我更想弄清楚：哪些事情现在就要决定，哪些应该等实现提供证据以后再说。

这个念头来自我自己的使用经历，也受到了 Ayman Nadeem 的 [《Plan mode is dead》](https://www.aymannadeem.com/artificial/intelligence,/developer/tools/2026/09/24/plan-mode-is-dead.html) 启发。作者对规划与执行相互割裂的反思，让我重新审视了一套已经用习惯的工作方式。

## 我批准了计划，结果还是需要重来

新开一个项目时，我往往会先进入计划模式。Agent，也就是能够探索代码并执行开发任务的 AI 助手，会梳理需求，问我几个问题，列出方案。我做选择，它整理成规划文档，然后开始执行。

这个过程看起来很认真。需求讨论过，方案比较过，连实现步骤都排好了。但等到东西真的做出来，结果常常不尽如人意：有些安排落地以后才显得别扭，有些问题事前没有想到，有些方案则是在看到成品后，才意识到还有更好的选择。

于是我又回去调整需求，重做一部分规划，再让它修改实现。

最初我容易把这归因于「前面没想清楚」。可如果每一次都要求自己再多想一点，最后会走向哪里？在写第一行代码之前，把所有交互、边界和未来变化都推演完吗？

**有些认识，需要先做出一点东西才会出现。** 把它们统统当作规划遗漏，会让我误以为只要文档足够详细，就能省掉探索过程。

## 问题有时出在决策的时机

计划模式里的提问，很容易给人一种正在消除不确定性的感觉。但回答了问题，不代表我已经拥有回答它的依据。

比如，新项目还没有跑通一个完整流程，Agent 就问我要不要为将来的多端同步提前设计抽象。两种方案都能说得通：现在做，后面可能省事；现在不做，眼下会简单一点。我当然可以选一个，但此时的选择有多少来自实际需求，又有多少只是对未来的想象？

这类提问如果一口气出现十几个，我会参与很多决策，却未必更理解项目。文档记录下来的确定性，可能超过了我们真正掌握的确定性。

我希望开工前的计划能够明确三件事：当前目标是什么，哪些边界不能越过，以及下一步要验证什么。对于尚无依据的部分，可以直接保留为假设。等第一条流程跑通，再决定是否需要进一步抽象。

这样，计划里的一句「暂时不知道」就有了实际用途：它指向接下来要做的实验。

## 让实现承担一部分探索工作

我更愿意尝试一种小步推进的方式：先理解足够开始的一部分需求，做出可以检查的结果，根据结果修正判断，再继续实现。

这里的关键是「可以检查」。如果 Agent 一次写完整个系统，最后才让我看，反馈依然来得太晚。更合适的第一步，是完成一条从输入到结果的实际路径，让我能观察行为，也让它能验证此前的假设。

拿一个假设的收藏工具来说，我可以先要求完成「输入链接、保存、重新打开后仍能看到」这条路径。试用时如果发现用户真正关心的是离线阅读，下一步的重点就会变化。这个发现，比提前讨论十种标签管理方案更能影响产品设计。

| 当前面对的问题 | 我希望怎么推进 |
| --- | --- |
| 还不确定用户需要什么 | 先做能试用的流程，检查需求是否成立 |
| 普通实现细节，容易修改 | Agent 结合现有代码选择，并完成验证 |
| 引入持续费用、改变数据去向 | 把代价和替代方案交给我判断 |
| 更改多个模块依赖的公共接口 | 先说清影响范围，再安排实现顺序 |
| 涉及不可逆的数据操作 | 提前确认方案、备份和恢复条件 |

表里的区别，主要在于判断需要什么证据，以及选错以后要付出多大代价。一个决定越难撤回，就越值得在行动前花时间。

## 少问我一些问题，但把重要的问题问清楚

AI 能够可靠处理的决策越多，需要我提前指定的细节就越少。这一点很有吸引力，但其中最重要的词是「可靠」。

一个局部实现是否合理，往往可以通过已有约定、类型检查和测试获得反馈。产品愿意承担多少持续成本、数据能否交给外部服务、以后由谁维护，则需要我的目标和约束。代码跑通并不能替我回答这些问题。

所以，我希望 Agent 在提出问题前，先探索能自行查明的事实。遇到需要我判断的取舍，再提供足够具体的上下文：推荐什么、为什么、代价是什么，以及什么情况下应该换一种选择。

「你想用方案 A 还是 B」把调研负担留给了我。「现有需求用 A 就能满足，B 会增加部署和维护工作；如果你需要跨设备共享，才有理由现在选 B」才让我有条件做决定。

这样的交互减少了提问的数量，也提高了每次提问的价值。

## 功能正常以后，我是否还理解这个项目

即使前面的循环运转顺畅，还有一个问题没有解决。

我让 Codex 修改项目，它很快生成大量代码，功能看起来也正常。但我可能并不知道：它为什么采用这种架构，哪些设计是它自行决定的，哪些隐藏假设影响了实现，新功能会牵动哪些既有模块。

等三个月后出现问题，我从哪里开始排查？如果我只能再开一个对话，让 AI 从头分析，那我对项目的理解并没有随着开发一起增长。

我之前在 [《AI coding 不该只会改代码》](/blog/codex-architecture-skill) 里讨论过模块边界和架构演进。这次的思考更进一步：即便 Agent 做出了合理的设计，我也需要知道这个设计依赖什么条件。条件变了，原本合理的选择就可能需要调整。

因此，我希望每次有实质性的设计变化时，留下简短、可核对的记录。比如，在前面那个假设的收藏工具中：

> 当前按单人、单设备使用设计，数据保存在本地。保存和读取集中在存储模块，界面不直接访问底层存储。已验证重启后数据仍可读取；跨设备同步尚未实现。若增加共享需求，需要重新评估存储方式和权限边界。

这段记录告诉我当前行为、适用条件、代码入口和验证范围。下次需求变化时，我知道该回到哪里继续讨论。

它也必须跟着实现更新。已经被推翻的假设如果仍以结论的形式留在文档里，会让后来的人更难判断。保留最初的计划有助于回顾，但维护项目需要的是对当前状态的准确说明。

## 多个 Agent，需要共同的约束和整体验证

多个 Agent 并行工作时，我更担心的事情是：每个任务单独看都做对了，合起来却建立在不同的假设上。

仍以收藏工具为例，一个 Agent 按单用户设计存储，另一个按多人共享设计界面。它们各自完成了任务，甚至各自的测试也能通过，但系统层面的约定已经冲突。

在我设想的协作方式里，并行开始前需要确认少量共同约束，例如用户模型、数据归属和公共接口。执行过程中，一旦发现要改变这些约束，就应当让受影响的任务知道。合并以后，还要检查贯穿多个模块的完整流程。

这也意味着，人不能只看每个 Agent 的「已完成」。更有用的汇报应该指出：哪些共同假设发生了变化，影响了哪些模块，整体行为经过了什么验证，还有什么尚未确认。

代码生成得越快，这些信息就越需要清楚。

## 我会保留规划，但改变它的位置

如果用《Plan 模式已死》来概括我的态度，那么我想放弃的，是每次新项目都先争取一份完整计划、再相信执行会自然抵达目标的习惯。计划模式作为集中梳理问题的工具仍有价值，尤其是在难以回退的操作和跨模块变更之前。

下一次开新项目，我会先明确目标、约束和第一步要验证的假设，让规划随着实现继续发生。我也会要求 Agent 交付关键决策及其依据，让自己能够回答：项目现在为什么这样工作，什么变化会让我们需要重新设计。

你也可以拿最近一次 AI 完成的功能试一试：离开原来的聊天记录，能否说清它依赖的假设，以及出了问题该从哪里查起？这比计划文档是否完整，更能检验我们有没有真正掌握正在构建的系统。
